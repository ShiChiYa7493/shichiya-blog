## 0. 这份文档怎么读

群务与 Warframe 是两个互不相干的子系统——数据源、状态模型、失败模式完全不同，共同点仅是「都往群里发消息」。因此它有独立的 spec。

写这份初稿时我没有你的细节要求（签到给什么、积分怎么花、违规管到多严），但把这些做成空白问题问你，你答起来累、也容易漏。所以我**先各定一个默认值**，标注理由。你只需要看哪条不对、改哪条。

## 1. 范围

已确认要做的四块（你在需求阶段勾选的）：

| | 内容 |
|---|---|
| 签到 / 积分 / 排行榜 | 每日签到得分、连签奖励、群内排名 |
| 娱乐小功能 | 随机推荐、今日运势之类的轻量互动 |
| 进群欢迎 / 退群提醒 | 事件触发的自动播报 |
| 违规管理 | 关键词与刷屏处置 |

明确不做：定时推送（已在主 spec 决定）。

## 2. 与 Warframe 域的关系

**同一个 Koishi 实例，完全独立的插件。**（实例合并是你确认过的决定。）

```
Koishi 实例
├── fuzzy-command      前置中间件，两域共用
├── warframe (fork)    Warframe 域
└── 群务插件组          本 spec ← 与上面互不引用
```

硬约束：**群务插件不得 import Warframe 域的任何东西，反之亦然。** 它们唯一的交集是共用 Koishi 的用户/群表。这条守住了，将来任何一边出问题都不会拖垮另一边——同实例部署最大的风险就是故障互相牵连。

## 3. 逐项设计（含默认值）

### 3.1 签到 / 积分 / 排行榜

**默认方案：**

| 决策点 | 默认值 | 理由 |
|---|---|---|
| 每日签到得分 | 基础 10 分 + 随机 0~10 分 | 纯固定值无聊，纯随机让人觉得不公平；固定打底+小随机是最常见的平衡 |
| 连签奖励 | 连续第 N 天额外 +N 分，上限 +30 | 鼓励回流又不至于让老人碾压新人 |
| 断签处理 | 连签清零，积分保留 | 惩罚只针对连签，不没收既得积分——没收会劝退 |
| 每日重置时点 | 本地时间 0 点 | 用**懒计算**（比对上次签到日期），不需要定时任务 |
| 积分用途 | **暂无消耗途径** | 见下方说明 |
| 排行榜 | 群内 Top 10，含自己的名次 | 只看前十找不到自己会没参与感 |
| 积分作用域 | **按群隔离** | 见下方说明 |

**两个需要你注意的默认决定：**

**积分暂无消耗途径。** 只能攒不能花的积分，新鲜感大约维持两周。但消耗途径（抽奖、兑换、赌博）是独立功能，且设计不当会引发群内矛盾（比如输光积分的人退群）。我的建议是先上「攒」，观察群友是否真的在用，再决定花在哪儿——而不是一开始就设计一套没人用的经济系统。

**积分按群隔离。** 同一个人在 A 群和 B 群的积分各算各的。理由是排行榜的意义在于群内比较；若全局共享，先加入的群会把后加入的群的榜单压死。代价是跨群用户要重复签到。

### 3.2 娱乐小功能

**默认只做两个：**

- `今日运势` —— 每人每天固定结果（用「用户ID+日期」做种子），同一天反复问结果一致
- `随机战甲` / `随机武器` —— 从物品库随机推一个，配合 Warframe 主题

**刻意不做的：** 抽卡、点歌、复读机、AI 闲聊。理由分别是——抽卡需要先有积分消耗体系（见上）；点歌涉及版权与外链；复读机是刷屏源；AI 闲聊是独立的一大块（成本、上下文、内容风控），不该混在群务里顺手做。

「每人每天固定结果」这个细节值得说明：如果运势每次都随机，群友会一直重摇直到摇出好结果，功能就废了。用种子固定住才有仪式感。

### 3.3 进群欢迎 / 退群提醒

**默认方案：**

- 进群：发一条欢迎，内容包含群规要点与 bot 的常用命令
- 退群：**只记日志，不在群里播报**

**退群不播报是刻意的。** 播报「X 退群了」除了制造尴尬没有实际作用，还会给退群的人二次伤害。若你确实想知道谁退了，走日志或私聊管理员更合适。

**这两个功能是 bot 主动发言**，与「不做定时推送」不冲突——它们由事件触发而非定时器触发，不需要调度器，风控风险也低得多（频率取决于真实的人员变动）。

### 3.4 违规管理

**默认方案：保守到近乎克制。**

| 行为 | 默认处置 |
|---|---|
| 命中关键词 | **仅提醒管理员，不自动处置** |
| 刷屏（N 秒内 M 条） | 撤回 + 提醒本人 |
| 广告识别 | **不做** |
| 自动踢人 | **不做** |

**理由：误判代价不对称。** 漏放一条广告的损失，远小于误踢一个正常群友的损失——后者基本不可逆，而且会让所有人对 bot 失去信任。广告识别尤其容易误判（正常聊天里出现链接、口令都可能中招）。

所以默认让 bot 只做「提醒」和「撤回」这类可逆动作，把不可逆的处置权留给人。等实际运行一段时间、看清群里的真实违规形态，再决定要不要收紧。

## 4. 技术选型

**优先用 Koishi 生态现成插件，不足处自研。**

⚠️ 这里有一条我此前给过、但后来**实测发现过于乐观**的判断，需要修正：我最初说「群务全是装一下就能用的现成插件」。实际搜索 npm 的结果是——

```
签到      koishi-plugin-checkin 等数个，但多为 2024 年的小插件，维护不活跃
进群欢迎  有（@aigio1064/koishi-plugin-welcome 等）
积分/排行榜  没搜到合适的通用插件
```

所以真实情况是**部分现成、部分自研**。选型要在实现阶段逐个评估：现成插件若维护停滞或行为不符，自研反而更省事——群务的逻辑本身不复杂，难点在数据模型和权限，不在算法。

**数据模型**：用 Koishi 内建的 database 服务（Warframe 插件已依赖它）。需要的表大致是「用户-群-积分-连签天数-上次签到日期」。

**每日重置用懒计算**，不引入定时任务——这与主 spec「不做推送因而无需调度器」的结论一致。

## 5. 风控

沿用主 spec 的约束，另加两条群务特有的：

- **欢迎消息也要限频**。有人恶意反复进退群时，bot 会跟着刷屏。同一用户短时间内重复进群只欢迎一次。
- **撤回权限依赖 bot 是管理员**。若 bot 不是管理员，刷屏处置要优雅降级为「仅提醒」，不能反复尝试失败操作。

## 6. 测试策略

- 积分结算、连签判定、运势种子：纯函数，直接单测。
- **测试不得对真实数据库执行写操作**，一律注入假 client 或内存库。
- 违规判定（刷屏窗口计数）需注入 clock，不依赖真实时间。
